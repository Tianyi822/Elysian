# Elysian Web 项目初始化提示词

你要创建一个名为 **Elysian** 的 Agent 运维工具项目。产品首先必须是一个可用、克制、面向运维人员的 Web 工具，而不是宣传页或角色展示页。

## 当前阶段

本阶段只实现 Web 侧和本地可运行的前端演示。暂不实现生产后端、真实云资源操作、真实 Kubernetes 操作、复杂 Agent 推理、用户认证和多租户。所有数据使用本地 mock 数据或浏览器内存状态，但组件边界要为后续接入 API、WebSocket 和 Cordis 服务保留清晰接口。

## 固定技术约束

- 使用 Bun 作为包管理器、脚本运行器和开发服务器运行环境。
- 使用 TypeScript。
- 使用 React。
- 使用 Vite。
- 使用现有成熟 UI 组件库或轻量 CSS 方案，不自行引入庞大的设计系统。
- 使用 Lucide 图标或项目已有图标库，不手写常见图标 SVG。
- 前端代码必须支持 `bun install`、`bun run dev`、`bun run build` 和 `bun run test`。
- 不使用 Node 专属 API 作为浏览器运行时依赖。
- 不在本阶段引入 Cordis 源码副本；通过类型化接口模拟未来的 Cordis service 和 event seam。

## 目标项目结构

项目采用 Bun workspace monorepo。首期重点实现 `apps/web`，但目录边界需要为后续服务端、Worker、技能插件和 harness 保留位置。

```text
elysian/
├── apps/
│   ├── server/                  # 生产服务入口
│   ├── web/                     # React Web 应用，本阶段主要实现
│   ├── worker/                  # 运维执行 Worker 入口
│   └── cli/                     # elysian 命令行工具
├── packages/
│   ├── foundation/
│   │   ├── contracts/           # 事件、Agent、技能、审批、审计类型
│   │   ├── config/              # 配置模型与校验
│   │   ├── logging/             # 日志与追踪
│   │   └── errors/              # 统一错误模型
│   ├── agent/
│   │   ├── agent/               # Agent 服务与生命周期
│   │   ├── agent-loop/          # 模型请求、步骤和轮次驱动器
│   │   ├── agent-persona/       # 职责模块与路由
│   │   ├── context/             # Agent 上下文与记忆
│   │   └── model/               # LLM provider seam
│   ├── harness/
│   │   ├── event-runtime/       # 事件接收、标准化和分发
│   │   ├── run-state/            # Agent run 状态机
│   │   ├── policy/               # 权限、风险和策略检查
│   │   ├── approval/             # 人工审批与接管
│   │   ├── tool-pipeline/        # 工具调用流水线
│   │   ├── retry/                # 超时、重试和幂等
│   │   ├── audit/                # 审计事件与回放
│   │   └── incident/             # 事故和告警流程
│   ├── skills/
│   │   ├── skill/               # 技能接口与 manifest
│   │   ├── skill-registry/       # 技能发现、版本、依赖和启停
│   │   └── skill-*/              # Kubernetes、云、数据库等技能
│   ├── capabilities/
│   │   ├── capability-broker/    # 受控能力调用入口
│   │   └── */                    # shell、云、集群、数据库等能力
│   ├── execution/
│   │   ├── worker-runtime/       # Worker 协议和任务调度
│   │   ├── sandbox/              # 沙箱接口和策略
│   │   └── worker-*/             # 本地、容器和集群执行后端
│   ├── persistence/              # 事件、会话、审计存储及适配器
│   ├── integrations/             # Webhook、监控、云和集群集成

│   └── bundles/                  # base、server、worker、web、headless 组合包
├── profiles/                     # development、readonly、production 等配置组合
├── vendor/                       # 仅在需要固定或修改时放置 Cordis
├── docs/                         # 架构、harness、技能、运维和 ADR
├── tests/                        # integration、contract、replay、e2e
└── scripts/                      # 构建、校验和开发脚本
```

`apps` 目录只负责启动和组合插件，业务逻辑放在 `packages`。`foundation/contracts` 是所有模块共享的稳定协议层；浏览器侧只依赖这些协议和 API adapter，不直接依赖 Cordis Context。技能通过 `capability-broker` 请求能力，不能直接持有 Shell、云平台或集群高权限对象。后续通过 `bundles` 和 `profiles` 组装不同部署形态，而不是复制多套应用入口。

## 产品定位

Elysian 是一个由 Agent 辅助处理运维事件的工作台。用户需要能够快速回答以下问题：

- 当前有哪些事故、告警和待处理任务？
- 哪些事件正在由 Agent 分析？
- Agent 得出了什么证据和判断？
- 它准备执行什么动作，风险是什么？
- 哪些动作需要人工审批？
- 执行结果、回滚状态和审计记录是什么？

界面应偏向高密度、可扫描、适合长时间使用的运维控制台。避免营销式 Hero、巨型标题、装饰性渐变、悬浮卡片堆叠和不必要的插画。

## 首屏与主要页面

实现一个带侧边栏的桌面优先 Web 应用，并保证窄屏下可以使用。

侧边栏至少包含：

- 总览
- 事件中心
- Agent 运行
- 技能目录
- 审批队列
- 审计日志
- 系统设置

首期页面至少包括：

### 总览

展示当前事件数量、处理中 Agent run、待审批动作、服务健康状态和最近活动。内容要来自 mock store，并支持刷新和筛选。

### 事件中心

展示事件列表，包含严重等级、状态、来源、服务、发生时间、负责人和当前 Agent。支持按严重等级、状态和来源筛选，并能打开事件详情。

### 事件详情

展示事件时间线、相关指标摘要、Agent 分析过程、证据、建议动作、风险等级、审批状态和执行结果。高风险动作必须显示明确的审批状态，不能伪装成已经执行。

### Agent 运行

展示 Agent 的当前状态、步骤、模型请求、工具调用、等待原因和错误。使用事件时间线表达状态变化，避免把模型输出渲染成没有上下文的聊天记录。

### 技能目录

展示技能名称、职责、版本、提供的能力、风险等级、启用状态和最近使用时间。技能详情展示 manifest 风格的信息，但当前只做前端展示和启停 mock 操作。

### 审批队列

展示需要人工确认的动作。用户可以查看目标、参数摘要、影响范围、风险说明、提出者和过期时间，并执行批准或拒绝。操作后要在界面中留下状态变化。

### 审计日志

展示事件、Agent 决策、工具调用、审批和执行结果的时间顺序记录。支持搜索、类型筛选和查看详情。

## 职责模块

使用中性的职责名词组织 Agent 能力。每个职责模块都应有明确的输入、输出、工具范围和风险等级，不要使用游戏角色名、角色立绘或角色人格作为产品功能依赖。

- **协调中心**：总协调与用户交互
- **事故指挥**：重大事故指挥
- **安全审查**：安全策略与审批
- **资源治理**：资源与成本治理
- **自动化编排**：工作流、脚本和工具编排
- **故障演练**：故障处置与压力测试
- **观测分析**：指标、日志和趋势预测
- **快速响应**：低延迟告警响应和临时修复
- **恢复工程**：可用性、灾备和恢复
- **根因诊断**：根因分析与实验诊断
- **知识呈现**：可视化、报告和知识表达
- **变更治理**：变更评审和经验沉淀
- **技能管理**：技能目录、版本和运维资产管理

这些模块不是可以绕过统一策略的独立权限主体。所有工具调用都必须经过统一 harness 的权限、风险、审批和审计流程。

## 前端架构要求

建议采用以下边界：

- `app`：应用启动、路由、全局布局和主题。
- `features`：事件、Agent、技能、审批、审计等业务模块。
- `components`：可复用的表格、时间线、状态标签、筛选器和面板。
- `stores`：mock 数据和前端状态；未来替换为 API client。
- `contracts`：事件、Agent run、技能、审批和审计记录的 TypeScript 类型。
- `adapters`：未来接入 REST、SSE、WebSocket 和 Cordis gateway 的接口位置。

业务组件不得直接散落 mock 数据。所有 mock 数据通过 store 或 adapter 提供。不要让 UI 组件直接依赖未来的 Cordis Context；浏览器侧只消费稳定的 API/event contract。

## Mock 行为

实现以下可交互行为：

- 事件筛选、排序和详情切换。
- Agent run 时间线的模拟刷新。
- 审批动作的批准、拒绝和过期状态。
- 技能启用和禁用的本地状态切换。
- 审计日志筛选和详情查看。
- 全局刷新按钮、加载状态、空状态、错误状态和无权限状态。

所有危险动作都必须明确标为 mock 或待接入，不得声称已经修改真实基础设施。

## 视觉要求

- 采用深色或浅色均可，但需要有明确的背景、正文、边框、成功、警告和危险色层级。
- 颜色不能只使用紫色或蓝色；严重等级要有清晰、可访问的视觉差异。
- 使用紧凑的间距和稳定的表格列宽，保证内容不会因为状态变化而跳动。
- 状态必须同时使用文字和颜色，不能只依赖颜色。
- 图标按钮需要 tooltip；有文字的主要操作按钮可以使用图标加文字。
- 页面区块使用自然布局，不要把整个页面拆成互相嵌套的卡片。
- 确保键盘焦点、对比度、表单标签和移动端溢出行为正确。

## 不要实现的内容

- 不接入真实 Kubernetes、SSH、云厂商或数据库凭证。
- 不执行 Shell、任意 JavaScript 或用户提供的脚本。
- 不实现生产级权限系统，只保留前端状态和接口占位。
- 不实现真正的模型调用，不把随机文本伪装成真实 Agent 结论。
- 不添加与当前工作台无关的落地页、营销文案或大型插画。
- 不为了展示 Cordis 而把内部实现细节暴露给普通运维用户。

## 验收标准

完成后必须满足：

- `bun install` 能安装依赖。
- `bun run dev` 能启动开发服务器并显示 Web 工作台。
- `bun run build` 构建成功。
- `bun run test` 至少覆盖路由、事件筛选、审批状态变化和技能启停。
- 页面在桌面和窄屏视口下没有明显重叠、溢出或不可操作控件。
- 首屏打开后直接进入总览工作台，不显示宣传页。
- 所有页面都有加载、空数据、错误和操作反馈状态。
- 代码中不存在真实凭证、真实基础设施地址或不可解释的网络请求。

## 输出要求

完成项目后，说明：

1. 实际创建的目录和主要模块。
2. 使用的 Bun、React、Vite 和 UI 依赖。
3. 如何启动开发服务器和运行测试。
4. 当前 mock 数据与未来 API/Cordis service 的替换位置。
5. 尚未实现的后端、harness 和执行 Worker 边界。

优先完成一个可运行、可浏览、可交互的运维工作台，再扩展页面数量。任何新增功能都必须保持事件、Agent、技能、审批和审计之间的职责边界清晰。
